# Sokuou 回流指南

> 回流者：使用中所得之一手经验，归于公共知识与原语也。
> Sokuou 之形，不由闭门构想而定，乃由众调用者之真实使用所揭示。

回流面向所有调用者，不要求每位使用者都能修改上游、维护 Rust 原语或同步其他项目。
报告问题、分享有效用法、修正文档与提交代码，皆为有效参与；无需先交付完整修复才能反馈。
使用 Sokuou 不附带必须贡献代码的条件。本文约定反馈与贡献的路径，不增加 MIT 许可之外的使用限制。

## Ⅰ · 何种所得值得回流

| 所得 | 建议去处 | 所需依据 |
|---|---|---|
| 库缺陷：数值、语义、API 契约 | 上游 Issue；可修复时提交 PR | 所用版本、最小复现、预期与实际行为；修复附回归测试 |
| 文档缺漏或容易误用之处 | 文档 Issue 或 PR | 误解发生的场景、相关 API 与修正建议 |
| 有效调用经验、参数选择、宿主接入经验 | 先留调用方总结；有复用价值时分享为 Issue 或文档 PR | 场景、选择依据、验证范围与适用边界 |
| 新曲线或缓动变体 | 先讨论适用场景；成熟者提交缓动族 PR | 数学定义或规格出处、端点与边界行为、实际需求 |
| 新原语、编排或错位等能力 | 先记录需求与局部方案，再讨论公共接口 | 可复现的使用场景、现有原语的不足、职责边界 |
| 帧循环、dt 获取、重绘、布局或框架适配 | 原则上留在宿主；通用经验可进入调用指南 | 分清宿主机制与纯数值解析，不把平台机制搬入核心 |

通用者宜回流，专用者先留调用方。
第二个独立场景是评估通用性的有力证据，并非凑够两处便自动纳入核心；仍须审视接口与定位。
明确的库缺陷与文档错误无需等到第二处出现才报告或修正。
未经验证的原语不预先实现——`animator.rs` 中 `Animator` / `Animation` 为预留，不代表已有可用编排器。

## Ⅱ · 如何参与

### 使用者：先留下可用的信息

1. 在调用方按 [INTEGRATION.md §Ⅳ](INTEGRATION.md#ⅳ--把调用所得留下来) 简述使用所得，判断属于库、文档还是宿主。
2. 查阅当前版本文档与[已有 Issue](https://github.com/GuitaristRin/Sokuou/issues)，能复用的讨论补充证据即可。
3. 向上游提交 Issue、文档建议或 PR。无法直接参与上游时，先保留可转交的本地记录。
4. 关联后续结论：已报告、待验证、局部规避、修复已合并、消费方已升级，是不同状态。

经验报告可沿用以下最小格式，不适用的字段可省略：

```text
类型：缺陷 / 文档 / 使用经验 / 能力提议。
场景：要实现什么交互；宿主环境；Sokuou 版本或提交。
事实：最小复现或有效用法；实际行为；验证方式与范围。
预期与依据：期望的行为；交互要求、数学定义或规格链接。
现有处理：调用方采用的方案及局限（如有）。
建议：文档澄清、原语修复或候选能力；尚不确定之处。
```

仅报告实际可分享的内容，复现宜尽量缩小，不要求公开完整应用源码。

### 贡献者：把经验化为可维护的改进

在 Sokuou 本仓贡献时，先读 [AGENTS.md](../AGENTS.md)。一次改进之序：

1. 说明场景、证据与改进边界；新能力先确认其为纯数值解析的职责。
2. 修正文档与原语；语义有变时，同时修订 [SOKUOU.md](SOKUOU.md)。
3. 行为 / 数值变更附回归测试，覆盖相关语义与边界；纯文档修正检查示例、链接及契约一致性。
4. 代码改动运行 `cargo test` 与 `cargo clippy`，无新增告警；提交约定从本仓守则。
5. 涉及破坏性变更，写明旧行为、新行为、受影响接口及迁移办法；由各消费方维护者按自己的发布流程升级。

回流不得破之不变量：

- 零外部依赖，纯 Rust，无 `unsafe`，无平台 `cfg`。
- 核心仍提供 `f64` 数值与相关原语；不扩张为渲染器、宿主时间线或全局服务。
- 保留弹簧解析解及已约定的时间策略；行为改变须明示、验证并同步正典。

### 上游修复尚未可用时

调用方可按自身交付需要采用局部规避、补丁或 fork，并记录适用版本、原因、局限与后续替换条件。
能够提交上游时，应关联 Issue / PR；不能提交时，保留可转交的证据。
上游修复可用后，由调用方维护者评估升级并清理已无必要的重复实现。
优先把通用修复带回共同原语，减少各项目重复维护；不要求外部使用者承诺统一期限或维护无权修改的仓库。

## Ⅲ · Agent 如何促成回流

在消费方执行动画任务的 Agent，应把以下习惯纳入正常收尾：

1. 先理解正典与调用指南，再按项目交互目标使用原语，补齐宿主适配。
2. 遇到摩擦，先分清误用、宿主问题、文档缺漏与库能力不足，留下证据。
3. 有可复用所得时，主动在任务总结中给出回流候选及最小报告，不只写“动画已完成”。
4. 按当前任务范围落实文档或代码改进；上游提交、发布与依赖更新遵循所在项目的协作规则。
5. 如实标注已完成的动作；本地草稿、已提交 Issue、已合并修复与消费方已采用不可混称。

回流的倾向是持续识别与分享通用价值，而非每次调用都新增原语，或自动修改所有消费方。

## Ⅳ · 经验如何进入文档库

- 调用方任务总结保留具体场景与证据，上游 Issue / PR 承接公共讨论。
- 已验证的通用用法进入调用指南，并说明适用边界；单一项目的参数不直接升格为全局规范。
- 原语的公共语义与不变量进入正典，API 细节进入 rustdoc，修复附相应测试。
- Git 历史记录已合并的改进与缘由；尚未合并的经验与问题可由 Issue 承载，不必伪造一份成功回流记录。

正典与实现应保持一致。发现冲突时，报告版本与差异，再修代码或修文档；不可借正典之名忽略当前版本的实际行为。
